## 0:00–3:00 仕組み

今日は GitHub Copilot Fusion が、モデルと処理の進め方をどう選ぶかを紹介します。後半は Framekit の実際の調査で観測したことを中心に、5つの使い方をお話しします。Framekit の機能紹介ではなく、Fusion に依頼し、結果を確認する流れが主題です。

Fusion は一つの固定モデルを意味しません。公開資料によると、要求に応じてモデルと実行パターンを選びます。Single は一つのモデルが取り組む方法です。Cascade は最初の回答を判定し、必要なら後続の工程に進みます。Critique は回答を別のモデルが批評し、そのフィードバックをもとに改訂します。どの経路が選ばれるかは要求ごとに変わり得ます。

関連する HyDRA 論文は、推論、コード生成、デバッグ、ツール使用という複数の能力軸を使うモデル選択の研究です。論文の実験結果はそのモデル群と価格前提での評価です。今回の私たちの CLI 実験で同じ削減率が出たという意味ではありません。HydraFusion の初期プレビューと現在の Fusion の説明にも時点の差があります。詳しい出典は資料に載せています。

## 6:00–13:30 5つの Tips

一つ目は、subagent に渡す仕事を具体的にすることです。委任を明示しなかった試行では、subagent 開始イベントは観測されませんでした。別の試行で委任を求めたところ、explore subagent の開始と完了が記録されました。その委任文には、読み取り専用、変更禁止、調査対象、根拠のパス、テスト案という条件が含まれていました。ただし権限と選ばれたモデルも違うので、指示だけが原因とは言えません。成果物と制約を明示し、親の回答も確認することが実用的です。

二つ目は、実行ループを比べる前に、何を数えるか決めることです。今回の時間はセッション開始から結果イベントまで、回数は観測できたモデル呼び出し開始とツール開始イベントで数えました。委任なしは約93秒、委任ありは約67秒でしたが、モデル、経路、権限、キャッシュや負荷が揃っていません。それぞれ1回の観測です。委任したほうが速いという結論にはできません。測定の定義と条件を一緒に残すことに意味があります。

三つ目は、品質と利用量を一緒に確認することです。同じ読み取り課題を High と Max で各1回実行しました。CLI が報告した AI credits は約5.311と27.379でした。これは請求額ではありません。両方とも主要ファイルと opacity の開始値を特定しましたが、提案したテストは実行していません。まず必要な品質条件を決め、それを満たすか独立に確かめてから effort を検討する、というのが今回の仮説です。この1組で一般的なコストや品質は比較できません。

四つ目は、具体的な根拠を求め、重要な説明を元のコードで確かめることです。Max の回答は、文字がアニメーションの600ミリ秒と遅延の間ずっと見えないように説明しました。しかしコードは opacity をゼロから一へ変化させるので、遅延後は徐々に見えてきます。ファイルの特定が正しくても、時間の説明まで正しいとは限りません。回答にパス、行、確認した事実、未実行のテストを含めてもらい、判断に影響する部分は自分で照合します。

五つ目は、予定と実行済みを分けることです。Max の経路計画には、solver と judge に続き、条件付きの repair がありました。記録にあったのは solver と judge の開始・完了で、repair の開始イベントはありませんでした。予定にあるから実行された、開始したから成功した、とは数えません。また Fusion の critic と CLI の subagent は別のイベントです。録画を公開するときは、アカウント情報や機密、プロンプトを確認します。

## 13:30–15:00 まとめ

Fusion は状況に応じてモデルと工程を組み合わせます。実際に選ばれた経路を観測し、委任の制約を明確にし、品質と利用量を別々に確認してください。予定と完了、実験の事実と仮説を分けることで、結果を説明しやすくなります。

今回のデータは探索的な少数試行です。速さや品質を一般化するには、条件を揃えた反復と、実際のコード変更・ブラウザ確認が必要です。ありがとうございました。
