## 0:00–3:00 仕組み

今日は GitHub Copilot Fusion が、モデルと処理の進め方をどう選ぶかを紹介します。後半は Framekit の実際の調査で観測したことを中心に、5つの使い方をお話しします。Framekit の機能紹介ではなく、Fusion に依頼し、結果を確認する流れが主題です。

Fusion は一つの固定モデルを意味しません。公開資料によると、要求に応じてモデルと実行パターンを選びます。Single は一つのモデルが取り組む方法です。Cascade は最初の回答を判定し、必要なら後続の工程に進みます。Critique は回答を別のモデルが批評し、そのフィードバックをもとに改訂します。どの経路が選ばれるかは要求ごとに変わり得ます。

関連する HyDRA 論文は、推論、コード生成、デバッグ、ツール使用という複数の能力軸を使うモデル選択の研究です。論文の実験結果はそのモデル群と価格前提での評価です。今回の私たちの CLI 実験で同じ削減率が出たという意味ではありません。HydraFusion の初期プレビューと現在の Fusion の説明にも時点の差があります。詳しい出典は資料に載せています。

ここで選択とオーケストレーションを分けて考えます。モデル選択は、どのモデルに仕事を渡すかです。オーケストレーションは、一つの回答を作る途中で、草案、判定、批評、修正などをどう組み合わせるかです。どちらもユーザーが毎回手作業で指定するとは限りません。公開ドキュメントが説明している範囲と、私たちが今回見たイベントの範囲は別々に扱います。

たとえば Cascade の図に repair と書いてあっても、その部分が条件付きなら毎回実行されるとは限りません。Critique についても、最初の HydraFusion の研究プレビュー記事と現行の Fusion ドキュメントでは、批評するモデルの説明が異なります。今日は現行の公式説明を中心に紹介し、昔の説明はその時点のものとして扱います。

## 3:00–6:00 操作記録

題材は Framekit の公開 Issue で、ドキュメントの hero が最初に表示されるときに文字やボタンが読みにくいという課題です。固定した同じコミットを使い、まずはファイルを変更せずに、実装の場所と検証案を探してもらいました。外部アクセスを禁止したため、CLI は Issue 本文を読まずにローカルコードを調べています。

ここで実際の操作を録画した GIF を表示します。［録画・公開内容の確認後に挿入］ プロンプト、経路、実際に観測できた工程、最終回答を順に見てください。工程の予定は、その工程が必ず動いた証拠ではありません。画面に出なかった内部の処理は推測しません。

今回は試行ごとに固定コミットから独立した作業場所を用意しました。安全のため読み取り専用とし、ファイルの変更、コミット、送信と外部サービスへのアクセスを禁止しました。対象は、初期表示で文字とボタンが読めるかという小さな課題です。回答には実装ファイルと、その動きを検証するテストの候補を挙げてもらいます。

画面を見るときは、まずどの依頼を送ったかを確認します。次に、記録された経路と、実際に開始して完了した工程を見ます。最後に回答のファイル名やテスト案を確認し、ソースを開いて照合します。結果の画面だけを見ると、途中で委任が起きたか、予定された修正工程が実行されたかは分からない場合があります。これを確認するために、イベントも記録しました。

## 6:00–13:30 5つの Tips

一つ目は、subagent に渡す仕事を具体的にすることです。委任を明示しなかった試行では、subagent 開始イベントは観測されませんでした。別の試行で委任を求めたところ、explore subagent の開始と完了が記録されました。その委任文には、読み取り専用、変更禁止、調査対象、根拠のパス、テスト案という条件が含まれていました。ただし権限と選ばれたモデルも違うので、指示だけが原因とは言えません。成果物と制約を明示し、親の回答も確認することが実用的です。

この試行で委任されたメッセージを確認すると、hero の実装とテスト基盤を探すこと、二つのテスト案を出すこと、根拠のパスを報告することが書かれていました。元の依頼の制約も委任文に現れています。ただし、リポジトリの指示ファイルが全部伝わったかをこの実験だけで確かめたわけではありません。公式ドキュメントでは、カスタム agent の subagent は既定でリポジトリ指示を受け取らず、設定で含められると説明しています。使う設定と、その時点のドキュメントを確認してください。

二つ目は、実行ループを比べる前に、何を数えるか決めることです。今回の時間はセッション開始から結果イベントまで、回数は観測できたモデル呼び出し開始とツール開始イベントで数えました。委任なしは約93秒、委任ありは約67秒でしたが、モデル、経路、権限、キャッシュや負荷が揃っていません。それぞれ1回の観測です。委任したほうが速いという結論にはできません。測定の定義と条件を一緒に残すことに意味があります。

この数え方には注意があります。ツールの開始イベントは、成功した操作だけを数えるものではありません。失敗や再試行も開始として数えます。モデル呼び出しの開始イベントも、外から見えない内部呼び出しを完全に表すとは限りません。完了イベントの request 数と一致しなかった箇所もありました。数値を比べる前に、同じ定義で取れているかを確かめる必要があります。

それでも、測定は役立ちます。ある実行が長かったとき、待機が長かったのか、ファイル調査を繰り返したのか、複数の工程が走ったのか、確認する手掛かりになるからです。答えの長さや速度だけで良し悪しを決めず、結果を得るためにどの工程が必要だったかを見ます。

三つ目は、品質と利用量を一緒に確認することです。同じ読み取り課題を High と Max で各1回実行しました。CLI が報告した AI credits は約5.311と27.379でした。これは請求額ではありません。両方とも主要ファイルと opacity の開始値を特定しましたが、提案したテストは実行していません。まず必要な品質条件を決め、それを満たすか独立に確かめてから effort を検討する、というのが今回の仮説です。この1組で一般的なコストや品質は比較できません。

品質の確認には、あらかじめ三つの観点を置きました。正しい hero の場所を示したか。通常の動きの設定で opacity がゼロから始まる点を見つけたか。最初の表示とボタンの可読性を確認するテストを提案したか、です。どちらも最初の二つはソースと照合できました。テスト案は出ましたが、私たちは実行していません。ここで分かるのは、限定された調査に対する回答の一部分であり、修正したコード全体の品質ではありません。

利用量についても、表示された単位をそのまま伝えます。トークン数、AI credits、premium request cost、実際の請求額は同じものではありません。プランや組織の契約、計測方法によって確認できるものが違います。私たちの資料には、CLI が出した値と未確認の範囲だけを書きました。

四つ目は、具体的な根拠を求め、重要な説明を元のコードで確かめることです。Max の回答は、文字がアニメーションの600ミリ秒と遅延の間ずっと見えないように説明しました。しかしコードは opacity をゼロから一へ変化させるので、遅延後は徐々に見えてきます。ファイルの特定が正しくても、時間の説明まで正しいとは限りません。回答にパス、行、確認した事実、未実行のテストを含めてもらい、判断に影響する部分は自分で照合します。

今回のような可読性の問題では、テキストや CSS の値だけでなく、実際のブラウザ画面も重要です。テーマ、画面幅、動きの設定によって見え方が変わります。既存のブラウザテストは動きを抑える設定を使っていたので、初期アニメーションを評価するときは条件を意識する必要があります。ただし今回はブラウザを使って測っていないため、実際のコントラストを数値で報告することはできません。

五つ目は、予定と実行済みを分けることです。Max の経路計画には、solver と judge に続き、条件付きの repair がありました。記録にあったのは solver と judge の開始・完了で、repair の開始イベントはありませんでした。予定にあるから実行された、開始したから成功した、とは数えません。また Fusion の critic と CLI の subagent は別のイベントです。録画を公開するときは、アカウント情報や機密、プロンプトを確認します。

この区別はデモを見せるときにも役立ちます。まず「予定」として何が表示されたか。次に、開始した工程と完了した工程は何か。最後に、ユーザーに返った回答は何か。三つを分ければ、条件付きの工程を余計に数えることを避けられます。実行を再生する場合は、録画であることを示し、ライブ実行だと誤解させないようにします。

## 13:30–15:00 まとめ

Fusion は状況に応じてモデルと工程を組み合わせます。実際に選ばれた経路を観測し、委任の制約を明確にし、品質と利用量を別々に確認してください。予定と完了、実験の事実と仮説を分けることで、結果を説明しやすくなります。

今回のデータは探索的な少数試行です。速さや品質を一般化するには、条件を揃えた反復と、実際のコード変更・ブラウザ確認が必要です。ありがとうございました。
