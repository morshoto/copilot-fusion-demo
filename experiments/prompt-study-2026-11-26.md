# Fusion High: 見直し指示と応答時間

## 問いと方法

同じ短い JavaScript 修正課題で、「0・undefined・null の3ケースを1回見直す」という文を追加すると、最終回答までの時間や観測された処理がどう変わるかを探索した。Fusion High、Copilot SDK 2.0.1、macOS。各試行を新規セッションで実行し、順序を交互に入れ替えた。2026-11-26、両条件10回ずつ。

課題と各プロンプト全文、実行日時、所要時間、最終回答、Fusionが通知したモデル・フェーズ・利用量は [記録](data/prompt-study-2026-11-26.json) にある。公開用にセッション・フェーズIDは除いた。所要時間はセッション作成を始めてから最終回答を受け取るまで。グラフの点はこの実測値そのもので、推定値ではない。

## 結果

| | 基本依頼 | 見直しを追加 |
|---|---:|---:|
| 試行数 | 10 | 10 |
| 中央値 | 10.12秒 | 10.71秒 |
| 最小–最大 | 8.75–14.30秒 | 9.75–12.44秒 |
| 観測された方式 | Cascade 10/10 | Cascade 10/10 |
| `??` を含む回答 | 10/10 | 10/10 |

文字列の有無は回答品質の完全な評価ではない。どちらが常に速い、あるいは見直しに0.59秒必要と結論づけられない。試行順は交互だが、負荷、キャッシュ、モデル側の非決定性は統制できず、他の課題への一般化もできない。

**ツールは無効で、ファイル操作・テスト実行を伴うエージェントループではない。** 見直しの指示をモデルが内部で実際に何回行ったかも観測できない。観測可能なFusionフェーズと、隠れた推論・エージェントのツール実行回数を混同しない。ツールを使うループの例は [既存のFramekit試行](prompt-loop-observation.md) にあるが、各条件1回であり分布や因果関係は分からない。

## 再実行

```sh
cd fusion-demo
./node_modules/.bin/tsx src/prompt-study.ts /tmp/fusion-prompt-study.json
cd ..
node experiments/render-prompt-chart.mjs
```

スクリプトはFusionを20回呼び出し、Copilotの利用量が発生する。生データにはセッション由来のIDが含まれる場合があるため、公開前に確認する。グラフ生成はリポジトリ内の公開用データを参照するため、再実行結果に差し替えるときは個人情報・IDを除去してから反映する。

## 実際の生成コードの検証

公開用データの20回答から関数を抽出すると、全件 `return config.timeout ?? 5000;` だった。`node experiments/verify-generated-code.mjs` は抽出コードが同一であることを確認したうえで、それぞれについて 0、undefined、null、2500 の4入力を Node.js で実行した。結果は80/80通過。これは実験後にこちらが実行したテストで、モデルがテストツールを実行したことや、あらゆる入力に対する品質を示すものではない。[生成コードとテスト結果の画像](../presentation/media/generated-code-verification.png) をスライドに掲載した。
