# Fusion effort 比較: 既存証拠と追試計画

対象: [#23](https://github.com/morshoto/copilot-fusion-demo/issues/23)。記録日: 2026-11-26。スライドへの統合は別作業。

## 利用可能な effort と制約

[GitHub の CLI 説明](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/choose-a-model) は Standard / High / Max と `--model fusion --fusion-tier` を記載する。[Fusion の説明](https://docs.github.com/en/copilot/concepts/models/copilot-fusion) は Fast もプラン別の表に載せているが、上記 CLI の選択肢には記載されていない。これは文書上の選択肢であり、実験に使うアカウント・CLI・ポリシーで利用できることの確認ではない。既存試行は CLI 1.0.115 の旧指定を使った。現行環境の `copilot` は PATH 上で見つからず、利用権限と実際の選択肢は未確認。

## 既存結果

詳細な条件、品質判定と出典は [元の記録](effort-quality-observation.md)。いずれも Framekit の同じ固定 SHA、読み取り専用の hero 調査だが、2組はプロンプトと品質基準が異なるため反復試行として合算しない。各条件 n=1 で、条件内のばらつきは算出できない。

| 組・条件 | 経路 | 品質 | 時間 | AI credits | 再試行 |
| --- | --- | --- | ---: | ---: | --- |
| Issue 本文なし High | Single / GPT-6.1 Terra | hero と opacity を特定、テスト提案は未実行 | 92.7秒 | 5.311 | 記録なし |
| Issue 本文なし Max | Cascade / Claude Opus 5.5 と判定工程 | hero と opacity を特定。初期コントラスト案に不足、説明に不正確な箇所。未実行 | 74.4秒 | 27.379 | 記録なし |
| 本文あり High 優先 | Single / GPT-6 Astra | 事前の3基準に合格、提案は未実行 | 未記録 | 34.426 | 基準に合格したため Max への追加なし |
| 本文あり Max 単独 | 未記録 | 図の文字をテスト対象に含めず不合格、提案は未実行 | 未記録 | 30.113 | 記録なし |

後者の High 優先と Max 単独は品質が異なるので同品質の費用比較ではない。表示値の差は丸め後で 4.313 credits、元の未丸め値から計算した差は元記録の 4.314 credits。30 credits の設定はソフト上限で、両者とも超過した。時間、Max の経路、再試行の有無は記録がない場合に推測しない。AI credits は利用量の単位で、実際の請求額ではない。[上限の説明](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/set-session-limit) の換算値だけでは、加入枠や実際の請求は判定できない。

この資料から一般的に最安の effort、難易度ごとの優劣、品質や時間のばらつきは判断できない。実務では先に必要な品質基準と検証手段を決め、合格した結果の総使用量と時間を比較する。High 優先が節約になるとは限らず、再試行・エスカレーションを行った場合はその利用量と時間も合算する。

## 追試の事前計画（未実施）

1. 実験前に実際の CLI バージョン、選択可能な effort、プラン・ポリシーと課金条件を確認。固定 SHA と独立 checkout、同一プロンプト・ツール権限・MCP・ネットワーク制約を明文化する。ログは非公開とし、公開結果には秘密、個人パス、セッション ID、非公開ログを含めない。
2. 簡単な課題と複雑な課題を各1つ事前に固定する。例えば前者は固定ソース中の特定と根拠提示、後者は #796 の本文を同梱した hero 調査。正解と採点表を回答前に固定する。複雑課題は元記録の3基準（原因とパス、初期・表示中の light/dark と全対象を含む2件のテスト案、4.5:1 と未実行の明示）を使用。簡単課題は対象の正しいパス、該当箇所の正しい説明、未確認事項の明示を全て満たせば合格。コードやテスト案が実行されていなければ実行成功と採点しない。
3. 利用可能な Standard / High / Max を各課題で各1回、独立セッションで実行するパイロットを想定。順序を課題ごとに変え、時刻・並行負荷・キャッシュ状態の不確実性を記録する。欠損や中断も除外せず報告。可能なら結果を隠した状態で採点し、判定根拠を保存する。
4. 各実行で effort、課題、SHA、権限、開始から完了までの秒数、完了状態、品質の各項目、観測経路、AI credits、再試行と理由を記録。再試行は元の失敗を残し別行とし、戦略全体の合計も示す。十分な合格例がある場合のみ同品質の利用量と時間を比較し、反復後は各値・範囲・件数を示す。1回だけではばらつきは不明とする。
5. パイロットは最大6セッション、各30 credits のソフト上限で設定値合計180 credits。過去の本文あり High / Max の2回合計は約64.539 credits で、課題や経路が異なる残り4回を予測する根拠にはならない。180 は実使用量や請求額の上限ではなく、応答完了による超過もあり得る。実行前に利用量と課金の見積もり・承認を得る。失敗、権限差、想定外の利用量、上限超過があれば停止し、追加反復はパイロットの観測と別途承認に基づき決める。

既存記録だけでは時間とばらつきの受け入れ条件を満たせない。追試を実行したという主張や一般化はしない。
